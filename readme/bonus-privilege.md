## 보너스: 권한 가로채기 탐지 현재 상태

연습 경보(`xdr/fixtures/privilege.json`, 가상 26건)만 다루는 부품입니다. 평범한 계정이 관리자 그룹에 들어가거나 처음 보는 곳에서 관리자 명령을 쓰는 형태를 다룹니다. 앞의 네 보너스와 같은 구조이고, ZTNA 판정기(`src/decider.mjs`)에는 **연결하지 않았습니다**(아래). 이 결과는 직접 돌린 연습이며 심판 판정이 아닙니다. 판정기의 기존 규칙과 `RULE_IDS` 5개는 바꾸지 않았습니다.

- `xdr/privilege/decide.mjs`: `decide(alert)` 하나만 내보내며 `import`가 없고 파일·네트워크·시계·난수도 쓰지 않습니다. 반환은 `{ action, confidence, reason }`이고 0.85 이상 block, 0.5 이상 alert, 그 아래 record입니다. `reason`은 근거 패턴 이름으로 시작하고 경보 설명 원문은 옮겨 적지 않습니다. 읽는 칸은 경보 설명(`rule.description`)과 그룹 이름(`data.group`)뿐이고, 시각·규칙 수준·경보의 mitre 칸은 읽지 않습니다. 연습 경보의 시각이 모두 09~16시라 업무 시간 밖 여부는 설명 문구로만 가릅니다. 낱말 세 개 이하의 짧은 부정문("관리자 그룹은 아닙니다.")과 "추가되지 않았습니다"처럼 일이 없었다는 문장은 일로 읽지 않습니다.
- `xdr/privilege/patterns.json`: 근거 패턴 4개(`admin_group_addition` T1078, `unfamiliar_admin_command` T1078, `off_hours_privileged_use` T1078, `session_admin_without_group_change` T1068)입니다. `decide.mjs` 맨 위 상수와 글자까지 같습니다. 근거는 요구대로 T1078과 T1068뿐입니다(ATT&CK 페이지로 2026-10-15에 확인). 관리자 그룹 추가를 ATT&CK가 직접 다루는 기법은 T1098.007이지만 근거에는 넣지 않았고, 그래서 `admin_group_addition`의 근거는 T1078의 일반 설명이며 그룹 추가를 직접 짚은 탐지 단서가 아닙니다. T1068은 소프트웨어 오류를 악용하는 기법이라 `session_admin_without_group_change`에서 그룹 변경 기록 없이 세션 권한만 관리자로 바뀐 경우의 의심 단서로만 쓰고 악용을 확인했다고 보지 않습니다.
- `xdr/privilege/respond.mjs`: block만 차단 후보(`block-candidates.json`, 만료 60분·근거 경보 번호 `alertIds` 포함)로 만들고 block·alert를 `xdr/alerts.log`에 한 줄씩 쌓습니다. 규칙의 대상은 **계정과 출발 주소의 쌍**입니다. 연습 경보에서 user01~user05는 공격과 정상 양쪽에 나와 계정만 막으면 정상 로그인이 막히기 때문입니다. 같은 쌍에서 정상 이벤트가 공격 시도보다 많거나, 계정·주소 형식이 아니거나, 내부·특수 주소면 후보에서 뺍니다. `blockingRule(후보, 계정, 주소, 시각)`은 만료 전 규칙만 돌려주는 확인 함수이며 아무 파일도 부르지 않습니다.
- `xdr/privilege/read-alerts.mjs`: 경보에서 시각·주소·계정·수준·설명만 뽑고 비밀값 모양은 가립니다. 확인용이며 `decide.mjs`는 불러오지 않습니다.
- 다시 실행: `npm run xdr:run -- privilege`(성공하면 화면에 아무것도 안 나오고 `xdr/privilege/result.json`을 씁니다), `node xdr/privilege/respond.mjs`(후보·알림), `node xdr/privilege/read-alerts.mjs`(경보 26건 / 뽑은 줄 26줄 일치 확인). `result.json`, `block-candidates.json`, `alerts.log`는 산출물이라 Git에서 제외했습니다. 이 보너스 전용 시험 파일은 만들지 않았습니다.

### 권한 가로채기 보너스의 남은 약점 (해소되지 않음)

- **판정기에 연결하지 않았습니다(보류).** 차단 후보는 파일로만 남고 실제 접속 격리는 일어나지 않습니다. 판정기 요청 계약(`docs/DECIDER_REQUEST.md`의 18개 항목)에 경보의 계정(`srcuser`)도 출발 주소도 없고, 요청의 `subjectId`는 가명이라 경보의 계정과 이을 근거가 없습니다. 계약에 없는 항목을 만들어 쓰지 않기로 했습니다. 운영 쪽이 계약에 값을 더해야 풀립니다.
- **쌍 규칙은 공격자가 같은 계정으로 다른 주소에서 오면 놓칩니다.** 정상 사용자를 막지 않기 위해 계정째·주소째 막지 않은 대가입니다. 후보 만료(60분)를 강제하는 곳도 없습니다. 후보 파일은 `respond.mjs`를 실행할 때마다 새로 쓰고, 만료는 `blockingRule`을 부를 때만 봅니다.
- **확신도 숫자와 글자 수 한도는 이 모듈이 정한 값입니다.** 0.5, +0.35, +0.05, 그리고 읽는 글자 수 한도 2000은 요구사항·ATT&CK·`patterns.json`이 정하지 않았고, 2000은 persistence 모듈의 값을 따랐습니다. 뚜렷한 신호 하나로 0.85(block)가 되는 구조라 pv-01·02·05·06·08·09 여섯 건이 정확히 block 경계(0.85)에 있습니다. 숫자를 바꾸면 한꺼번에 흔들립니다.
- **규칙은 연습 경보의 문장에 맞춰져 있습니다.** "원격 주소", "곧바로", "처음 보는 주소", "수업 시간 밖" 같은 낱말을 읽으므로 심판 경보가 다른 문장이면 놓치거나 alert로만 남을 수 있습니다. 같은 주소에서 여러 계정이 들어가는 것, 빠졌다가 다시 들어오는 것, 방금 관리자가 된 계정의 명령은 연습 경보 문구를 따른 보조 신호이며 ATT&CK가 직접 정한 것이 아닙니다. "자기 계정 종류를 조회"(pv-13)는 `patterns.json`에 없는 낱말인데 애매한 경보(alert)로 남기려고 의심 단서로만 읽습니다.
- **한 건씩 판단합니다.** "직전에 같은 계정이 관리자 그룹에 추가됐다"는 다른 경보는 읽을 수 없고 같은 경보 설명 안의 말만 읽습니다. 업무 시간 밖은 시각이 아니라 설명 문구에서만 읽습니다.
- 같은 쌍에서 공격 1건과 정상 1건이면 후보로 남습니다(정상이 더 많을 때만 보호). IPv6 주소는 후보에서 빠집니다(알림 로그에는 남습니다). `alerts.log`는 계속 쌓이고 정리 규칙이 없으며, 다시 실행하면 줄이 중복됩니다.
- 시험 자료가 가짜이고 심판 경보의 형식은 이 저장소에서 확인할 수 없습니다. 이 보너스는 `decide.mjs` 한 파일만 심판이 불러 쓰는 구조라 `respond.mjs`의 후보·알림은 심판이 보지 않을 수 있습니다.
